# 什么是SDD？一篇讲清楚规格驱动开发

2025年，AI辅助编程领域出现了一个新概念：**SDD**，全称 Spec-Driven Development，中文叫**规格驱动开发**。

它不像 "vibe coding"（氛围编程）那么出圈，但可能是更值得关注的一种开发方式。

## 什么是SDD？

**SDD 的核心思路是：先把需求写成一份清晰的"规格文档"，再让 AI 根据这份规格来生成代码。**

这里的"规格"（Spec）不是产品需求文档（PRD），而是一份更技术性的描述，要明确告诉 AI：

- 这个功能要做什么（输入输出是什么）
- 边界条件是什么
- 界面长什么样
- 交互流程是怎样的

听起来有点眼熟？没错，这其实就是传统软件开发里的"需求规格说明书"，只不过现在是用自然语言写给 AI 看的。

**SDD 和传统开发、vibe coding 有什么区别？**

传统开发是：需求 → 自己写代码 → 产出软件
vibe coding 是：需求 → AI 生成代码 → 改一改能用就完事
SDD 是：需求 → 写成规格文档 → AI 根据规格生成代码 → 人工审核 → 迭代

SDD 和 vibe coding 的区别在于：它多了一层"先把需求写成规格"的动作。这个动作解决的是"需求说不清楚"的问题——因为规格文档越清晰，AI 生成的代码越可靠。

## 为什么会出现SDD？

用自然语言指挥计算机完成业务需求，一直是软件开发和编程语言理论的"圣杯"。

过去两年，随着大语言模型（LLM）的发展，这个梦想突然变得可行了。早期的 AI 编程助手如 GitHub Copilot，主要帮我们生成代码片段。但随着模型上下文窗口的扩大，直接用自然语言需求来构建软件变得越来越容易。

为了更好地实现这一点，主流的 AI 编程工具通常会将开发过程分为两个阶段：

1. **规划阶段**：理解需求、设计约束、编写规格文档
2. **实现阶段**：根据规格文档生成代码

这个"先规划、后实现"的思路，正是 SDD 的核心。

## SDD在实践中是如何工作的？

不同的工具提供了不同的工作流程。

**预定义工作流的工具**（如 Amazon Kiro、GitHub Spec-Kit）会提供比较固定的结构：需求输入 → 规格生成 → 代码实现。你只需要按步骤填写，工具会自动帮你完成整个流程。

这种方式的优点是：流程清晰，适合新手入门。缺点是：当需求发生变化时，修改规格比较麻烦——你需要在工具定义的模板里来回调整，灵活性受限。

另一种更灵活的方式是**开放规格**（OpenSpec）：不依赖特定工具的模板，而是用 Markdown 文件自行定义规格文档。通过 Cursor Rules 或 AGENTS.md 文件来约束代码生成的风格和技术要求。

我个人更倾向于**预定义工作流的方式**。因为这种方式通常要求你写出更详细的规格，而越详细的规格意味着 AI 生成代码的可靠性越高。这不是工具的问题，而是"把需求写多细"决定了最终代码的质量。

## 什么是规格？好的规格应该什么样？

规格（Spec）和产品需求文档（PRD）不是一回事。

PRD 描述的是"做什么业务"，规格描述的是"软件应该有什么行为"。一份好的规格应该明确定义：

- 外部行为：输入输出映射、前置条件、后置条件
- 约束条件：接口类型、集成契约
- 交互逻辑：状态机、流程步骤

业界常用的方法是 **Given / When / Then** 模式，来自行为驱动开发（BDD）：

- **Given（给定）**：描述初始状态或前提条件
- **When（当）**：描述触发某个动作或事件
- **Then（那么）**：描述期望的结果

举个例子，写一个"用户登录"功能的规格：

```
Given: 用户已注册，账号为 test@example.com，密码为 123456
When:  用户输入正确的账号和密码，点击登录按钮
Then:  系统显示登录成功，跳转到首页

Given: 用户已注册，账号为 test@example.com
When:  用户输入错误的密码，点击登录按钮
Then:  系统显示"密码错误"，停留在登录页面
```

这种方法的好处是把"在什么情况下会发生什么"写得清清楚楚，AI 很难理解歪。

除此之外，好的规格还应该：

- 使用领域术语，描述业务意图而不是技术实现细节
- 结构清晰，用统一的风格定义场景
- 简洁完整，覆盖关键路径但不罗列所有边界情况

## SDD的风险和挑战

SDD 目前还存在一些争议和挑战。

**第一个争议是：规格和代码，谁是最终需要维护的？**

较为激进的观点认为，我们可以抛弃代码，将规范视为唯一需要维护的真理来源。在这种观点看来，代码是一种副产品，是需求和编译后的二进制文件之间的中间产物。

相比之下，较为传统的技术人员——比如我——认为规范仅仅是驱动代码生成的要素，就像在测试驱动开发中一样。可执行代码仍然是需要维护的真理来源。

这两种观点会导致完全不同的工作流程：激进派只维护规格，随时用 AI 重新生成代码；传统派把规格当作起点，代码才是终点。

**第二个挑战是：AI 生成代码不是确定性的。**

从规格到代码的转换过程存在不确定性。这意味着升级和维护时会遇到问题。规格漂移（spec drift）和幻觉是本质上难以避免的问题——我们仍然需要确定性很强的 CI/CD 流程来保障软件质量。

**第三个挑战是：写出一份好的规格，比想象中难。**

这是我实际使用 SDD 开发一周后最深的感受。

简单、边界清晰的需求，用 SDD 效率提升非常明显。你只需要把功能描述清楚，AI 生成的代码基本就是你要的。

但复杂需求就不是这么回事了。你以为已经写得很清楚了，AI 实现出来却总有几处不对——漏掉了某个细节，或者理解错了某个边界条件，甚至出现幻觉生成了一些不在预期内的功能。

这时候你会发现，问题不在 AI，而在于**你自己没把需求写够细**。一个功能你可能自以为说清楚了，但规格文档里漏掉了某个交互细节，AI 就按它的理解去实现了。

换句话说，SDD 只是把"需求写不清楚"这个问题暴露出来了——以前需求写不清楚的代价是后面改代码，现在需求写不清楚的代价是 AI 生成一堆不对的代码。本质上是同一件事，只是反馈来得更快了。

## 总结

SDD 不完美，但它代表了一个方向。

它解决的问题是把"设计和实现分开"——先想清楚要什么，再让 AI 动手。在 AI 编程时代，**写好需求文档变成了核心竞争力**，因为你和 AI 之间的唯一桥梁就是那份规格文档。

SDD 能否成为主流，很大程度上取决于大模型和 AI Agent 技术的发展。我持乐观态度——随着模型能力的提升，AI 对模糊需求的理解会越来越准确，而"先把需求写清楚"这个能力也会反过来推动我们更好地思考需求本身。

至于规格和代码的关系，哪个是"最终真相"——这个问题可能还会争论下去。但对于今天的实践者来说，更重要的是：**先试着写一份足够详细的规格，然后看看 AI 生成的代码是否是你想要的。**
