2026 年 4 月，Andrej Karpathy 在 GitHub 上发了一份 gist：75 行 Markdown，不到 2000 字。一周之内，它拿到了 15000 多个 star；相关推文的浏览量超过 1700 万。

Karpathy 是 OpenAI 的联合创始人之一，后来在特斯拉担任 AI 总监，目前在 Anthropic。他在 AI 圈的影响力很大，甚至有人称他为 AI 的“教导主任”。

这份 gist 的标题叫《LLM Wiki》。它描述的是一种工作流：让 LLM 持续维护一个知识库。

## 它要解决什么问题

先说一个熟悉的场景：RAG，也就是检索增强生成。把一批文件交给大模型；每次提问时，它从文件中检索相关片段，再拼出答案。下一次问到相近的问题，它又重新检索、重新拼接。

这种方式有一个限制：每次提问都接近从零开始。一个需要综合五份文档的问题，LLM 每次都要重新找到相关片段，再把它们组织起来。中间没有形成可复用的积累。

RAG 有点像解释器：每次运行时重新求值。

Karpathy 提出的思路不同。原始资料放在 `raw/` 目录中，LLM 做一次性的处理：读完资料、提取关键信息、更新相关 wiki 页面、建立交叉引用、标记矛盾、追加日志。处理后的页面放在 `wiki/` 目录里。之后再提问时，LLM 直接阅读这些已经整理过的页面。

这更接近编译器：资料进入系统时编译一次，之后基于编译产物推理。知识不必每次重新推导，也可以逐渐积累下来。

## 什么是 LLM Wiki

一句话说，LLM Wiki 是一个由人和 LLM 共同管理、持续生长的知识库。

人负责收集资料、判断资料质量、决定关注的方向，以及提出问题。LLM 负责那些琐碎但容易遗漏的维护工作：读资料、写摘要、更新索引、建立交叉引用、标记矛盾、追加日志。

### 三层结构

整个系统可以分成三层。

**第一层：`raw/` — 原始资料**

文章、PDF、网页剪藏、截图都放在这个目录。LLM 只读不写，它们是事实来源。即使 wiki 出了问题，也能从这里重新构建。

**第二层：`wiki/` — 结构化知识**

这一层由 Markdown 文件组成，包括摘要页、概念页、对比分析、索引和日志。它主要由 LLM 创建和维护。

**第三层：Schema — 规则文件**

它可以是一份 `CLAUDE.md`，也可以是 Codex 使用的 `AGENTS.md`。规则文件告诉 LLM：

- 这个 wiki 关注什么问题
- 目录如何组织
- 页面命名遵循什么约定
- 处理新资料时需要做什么、不能做什么

没有这份文件，LLM 只是通用聊天机器人。有了它，LLM 才能在一个稳定的边界内维护 wiki。

规则不需要一开始就写得完整。实际使用中，随着资料和问题变多，它会慢慢长成更合适的样子。

### 三种日常操作

**Ingest（摄入）**：把新资料放进 `raw/`，交给 LLM 处理。它会阅读资料、写摘要、更新索引和相关页面、标记矛盾，并追加日志。一份资料有时会带来十几个页面的更新。

**Query（查询）**：提出一个问题。LLM 先读 `index.md` 找到相关页面，再跨页面综合信息，给出带引用的回答。那些意外发现的联系或对比，也可以写回 wiki，不必只留在聊天记录里。

**Lint（检查）**：定期让 LLM 做健康检查：有没有相互矛盾的论述，有没有无人链接的孤儿页面，有没有被新资料推翻的旧结论，或者还有哪些重要概念没有页面。这类维护工作很容易被人跳过。

### 一个帮助理解的类比

实际使用时，我会一边开着 LLM agent，一边打开 Obsidian。LLM 根据对话编辑 wiki，我实时浏览结果：点开链接、看图视图、阅读更新后的页面。

- Obsidian 是 IDE
- LLM 是程序员
- Wiki 是代码库
- 人负责决定方向，并检查结果

## 怎么搭一个 LLM Wiki

这一节只保留一套够用的做法。

### 前置条件

开始之前，可以先问自己两个问题：

1. 有没有一个明确的问题，需要借助知识库解决？
2. 手头有没有足够多的优质相关资料？

缺少其中任意一个条件时，知识库很容易变成“为了建而建”。

### 第一步：建目录

在电脑上建立一个 git 仓库，放入三个部分：

```
my-wiki/
  raw/          ← 原始资料，只读
    inbox/      ← 待处理的新资料放这里
    sources/    ← 已处理资料的归档
  wiki/         ← LLM 维护的结构化知识
    index.md    ← 内容索引，查询时优先读取
    log.md      ← 按时间追加的操作日志
  CLAUDE.md     ← 规则文件
```

### 第二步：选工具

需要一个能读写文件、能遵循规则文件的 LLM agent。常见选择包括：

- **Claude Code**：终端中的 Claude agent，会自动读取项目内的 `CLAUDE.md`。
- **Codex CLI**：OpenAI 的终端 agent，读取 `AGENTS.md`。
- **Cursor**：IDE 中带有 agent 模式，也支持规则文件。

我使用的是 Claude Code。工具本身不是关键，能否稳定遵循规则、读写本地文件，通常更重要。

### 第三步：写 Schema

`CLAUDE.md` 决定了 wiki 的运行方式。最少需要定义几件事：

- 这个 wiki 要解决的问题
- 目录结构和分类方法
- 页面命名约定
- Ingest 的步骤：读资料、写摘要、更新索引、更新相关页面、追加日志
- Query 的步骤：先读索引、找到相关页、综合回答、把值得保留的回答写回 wiki
- 语言策略，例如用中文解释、用英文保留例句

先写一份能跑的版本即可。跑几次 ingest，观察 LLM 做错了什么，再把约束补进规则中。

### 第四步：跑第一次 Ingest

1. 把第一份资料放进 `raw/inbox/`。
2. 告诉 LLM：“处理 `raw/inbox/` 里的新资料。”
3. 查看它更新了哪些页面，摘要是否准确，有没有补出原文没有的信息。
4. 根据观察调整 `CLAUDE.md`。
5. 再放入第二份资料，重复这个过程。

日常节奏也很简单：有新资料时做 ingest；有疑问时直接查询；用了一段时间后跑一次 lint。

### 可能会用到的工具

- **Obsidian**：适合浏览 wiki。图视图能看到页面之间的关联，Dataview 插件可以运行查询。页面之间可使用 Obsidian 风格的 `[[双向链接]]`。
- **qmd**：本地搜索工具。wiki 较小时靠 `index.md` 导航已经足够；资料变多后，可以用它做 BM25 和向量混合搜索。
- **git**：wiki 本质上是一组 Markdown 文件，版本管理、分支和回滚都很自然。

## 一次英语学习实践

我用 LLM Wiki 搭过一个英语学习系统。它从 2026 年 5 月底开始运行，到写下这些内容时大约一个月。下面是一些实际感受。

### 先走过一段弯路

刚读到 Karpathy 的 gist 时，我觉得这个思路很有道理，却想不出应该用它解决什么。我最初尝试的是一个大而全的“第二大脑”：把生活中的各种信息都丢进去，期待未来会有用。

很快就放弃了。那个系统缺少具体问题，也没有足够稳定的资料来源。它逐渐变成了一个空的容器。

后来换成学英语。目标是 CEFR B2，大约一年时间，每天投入 30 分钟左右。

这个场景恰好具备两个前置条件：

- 有明确的问题：目前大概认识 1000 个基础词，希望系统提升到 B2 水平。
- 有足够多的优质资料：Oxford 3000/5000 词表、BBC Learning English 的听力与 transcript、British Council 的分级阅读、Cambridge 的语法资料。这些大多是免费且质量较高的来源。

方向确定后，wiki 才开始产生比较具体的价值。

### 英语水平画像

这套系统持续追踪我的英语水平，这也是传统学习方式不太容易做到的部分。

每天完成学习任务后，LLM 会批改输出：填空、造句、改错和自由写作。再根据表现更新 wiki：

- **词汇掌握程度**：每个词分为三个等级。L1 是刚学过，L2 是能在控制练习中用对，L3 是在自由输出中也能用对。如果后来在自由输出里拼错，等级会回退。它记录的不是“是否学过”，而是实际掌握程度。
- **语法错误模式**：同一个错误出现过几次，发生在控制练习还是自由输出中，连续正确几次后能转为抽查。例如 `want to do` 这个结构，我到第 5 次才真正记住；前 4 次都在不同场景里漏掉了 `to`。系统记录每一次表现，连续 3 次正确后才标记为“已修复”。
- **弱项清单**：根据实际错误累积而来，每一条都有出现日期和修复进展。它比“我觉得自己语法不好”更具体，例如“现在完成时和具体时间混用，06-10 修复，06-18 回退，06-22 再次修复”。

### 根据画像定制内容

画像并不只是记录，也会影响每天的学习计划。

有一天，我在自由输出中写了 `I have been to Beijing last year`。这是现在完成时与具体时间混用：加上 `last year` 时，应该写成 `I went to Beijing last year`。系统把它记录为一种错误类型，第二天的 warm-up 就安排了 1 到 2 道相关改错题。当天的新内容也会压轻一些，因为先要处理结构性的错误。

另一些时候，如果错误很少，只有 0 到 1 个结构性错误，系统不会一味增加复习，而会触发“前摄语法”：主动引入新的语法点，例如 present perfect 和 past simple 的对比。

根据实际表现调整计划，是静态教材和通用学习 App 较难提供的体验。它也依赖一个前提：记录和判断本身不能离事实太远。

### 需要留意的风险

LLM 会产生幻觉。它可能编造不存在的语法规则，错误标记一个词的 CEFR 等级，或者把某个用法的因果关系解释反了。

在学习场景里，这个问题尤其麻烦。学习者不一定能立刻识别出错误，错误内容一旦被写进 wiki 并反复强化，代价可能比没有使用工具更大。

我采取了一些防范措施：

- 原始资料尽量来自 Oxford、BBC、British Council、Cambridge 等权威来源；wiki 里的知识必须能追溯到 `raw/` 中的源文件。
- 在 `CLAUDE.md` 中定义来源分级：A 级权威、B 级优质、C 级真实材料、D 级 LLM 生成。D 级内容不能被当作权威依据。
- 定期运行 lint，检查相互矛盾的内容。

这些措施只能降低风险，不能消除风险。学习者本人不是英语教师时，仍有一些错误不容易被发现。这大概是使用 LLM Wiki 时始终要保留的一点警惕。

## 写在最后

LLM Wiki 提供的并不是一种替代思考的方法。它更像是把整理、索引、交叉引用和维护这些长期容易堆积的工作交给了 LLM。

对有明确目标、也有一批可信资料的人来说，它可以让知识不只停留在收藏夹和聊天记录中。对问题还没有成形、资料也很稀少的场景，它未必比一个简单的文件夹更合适。

知识库会不会随着资料增加而真正变得有用，可能仍取决于人愿意在什么问题上停留，以及愿意相信哪些材料。
